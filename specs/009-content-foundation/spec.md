## 取代说明（Supersedes 005-content-pages）

本 Spec **取代** `005-content-pages`（状态 Draft，从未按其自身规定落地）。

- 005 规定（spec.md 第 143 行、FR-005/FR-006）：教学内容以 **TypeScript/JavaScript 数据模块**形式存放于 `packages/content`，**暂不引入数据库或 CMS**。
- 这与项目最新决策——**教学内容数据下沉到后端 SQLite、由 API 提供、前端拉取渲染**——直接冲突。
- 现实状态：005 也未被遵守，内容被**硬编码进各 `page.tsx`**，`packages/content` 至今为空壳。
- 取代理由符合宪法**原则 I（关注点分离）**：内容持久化属于「数据与运维层」，由后端拥有并通过 API 暴露，比「前端 TS 数据模块」更合规。

后续模块迁移（010 Job / 011 Code / 012 Lab / 013 Chat）均建立在本 Spec 的基础设施之上。

## Clarifications

### Session 2026-06-30

- **数据库选型**：v1 明确采用 **SQLite**（即「有数据库的版本」），够用即可；更重的数据库留待后续版本。
- **旧方案 `packages/content` 的处置**：**归档 / 暂存，不做删除式改动**，但本程序**不采用**该方案。允许在其 `README` 标注「已归档，不再使用」，代码与目录保持原样。
- **整条迁移线的数据归宿**：不仅 009，后续每个 Spec（010 Job / 011 Code / 012 Lab / 013 Chat）都 MUST 将各自的教学内容数据迁入 SQLite，由后端 API 提供。
- **「数据」边界澄清（对 Lab / Chat）**：入库的是**静态教学文本 / 步骤内容**；交互行为（滑块联动、概率分布重算、流式与动画）**保留在前端**，不入库、不视作内容数据。Job / Code 近乎纯数据；Lab / Chat 为「数据入库 + 逻辑留前端」。
- **SQLite 文件不入版本库**：内容的 git 唯一来源是**文本型 JSON fixtures**；`.db` 文件为由 fixtures 生成的产物，应被 `.gitignore` 排除并移出跟踪（`git rm --cached`，保留本地文件），避免二进制库在版本控制中频繁 diff / 冲突。具体落地在 `/speckit-plan` 与实现阶段执行。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 学生在术语页看到由后端提供的教学内容 (Priority: P1)

学生打开「名词解释 / Jargon」页面，看到按分类组织的 LLM 术语树；点击任一术语，右侧展示其通俗解释与技术解释。**这些内容由后端提供，而非写死在前端代码里。**

**Why this priority**: 这是本 Spec 唯一面向最终用户、可见可验证的切片，证明「DB → API → 前端渲染」全链路打通。没有它，本 Spec 只是不可观测的基础设施。选 Jargon 是因为它在新前端已迁移完整、改造面最小、风险最低，适合当 canary。

**Independent Test**: 启动前后端，访问名词页 → 看到与改造前一致的术语与分类（数量以入库 fixtures 为准）、通俗/技术解释；通过浏览器开发者工具确认内容来自 `/api/content/jargon` 网络请求，而非前端 bundle 内联常量。

> **数据事实更正**：现有 `jargon/page.tsx` 内联 `CATEGORIES` 实际为 **36 词条 / 6 分类**（侧边栏曾硬编码「43 个术语」的标签与实际数据不符，属旧标签遗留）。本 Spec 以**实际内联数据（36 词条）为迁移源**，并将页面词条计数改为**由数据动态计算**，不再硬编码。旧 `Jargon.dc.html` 含更多词条与「关联词条」导航，作为**未来内容增强**（需补 `related` 数据），不在 009 范围。

**Acceptance Scenarios**:

1. **Given** 内容已 seed 入库，**When** 学生访问名词页，**Then** 页面展示全部分类与术语，数量与入库 fixtures 一致（当前 36 词条 / 6 分类），且计数为动态显示。
2. **Given** 学生在名词页，**When** 点击某术语，**Then** 右侧显示该术语的通俗解释与技术解释。
3. **Given** 学生尚未选择术语，**When** 进入名词页，**Then** 右侧显示占位提示（「从左侧选择一个术语查看详情」）。
4. **Given** 后端不可用或内容为空，**When** 学生访问名词页，**Then** 页面显示友好的空/错误状态，不白屏、不报未捕获异常。

### User Story 2 - 内容维护者通过编辑数据文件并运行导入来更新内容 (Priority: P1)

内容维护者修改某个术语的解释（或新增一条术语），编辑对应的内容数据文件后运行一条导入命令，刷新页面即可看到更新——**全程无需改动任何前端组件代码**。

**Why this priority**: 「内容与代码解耦」是整个迁移程序的核心收益，也是后续 4 个模块共享的工作方式。导入必须可重复执行（幂等），重复导入不产生副作用或重复数据。

**Independent Test**: 编辑某术语数据文件的一个字段 → 运行导入命令 → 刷新名词页看到更新；再次运行导入命令 → 数据不重复、不报错（幂等）；对未改动的数据，导入为无操作。

**Acceptance Scenarios**:

1. **Given** 一份内容数据文件，**When** 首次运行导入命令，**Then** 内容被写入存储且数量校验通过（条数与数据文件一致）。
2. **Given** 已导入过的内容，**When** 在数据未改动的情况下再次运行导入，**Then** 不产生重复记录、不报错（幂等无操作）。
3. **Given** 维护者修改了某条内容的字段，**When** 运行导入，**Then** 仅该条记录被更新，其余不变。
4. **Given** 数据文件条数与预期校验值不符（如提取出错），**When** 运行导入，**Then** 导入**显式失败并报告差异**，不静默写入残缺数据。

---

### User Story 3 - 后续模块开发者复用同一套内容基础设施快速接入 (Priority: P2)

开发者在迁移下一个模块（Job/Code/Lab/Chat）时，复用已有的内容存储模型、导入机制、内容读取 API 模式与共享类型定义，只需提供该模块的数据文件与少量模块特定的读取端点，而无需重新设计数据层。

**Why this priority**: 基础设施一次设计、四次复用，避免重复造轮子（宪法原则 III/IV）。这是面向未来 Spec 的价值，非本 Spec 的用户可见产出，故置于 P2。

**Independent Test**: 审阅本 Spec 交付的存储模型/导入器/API/类型是否为「模块无关」的通用结构（以 `module` 维度区分），并能在不修改其核心的前提下，仅通过新增数据文件与端点接入一个新模块。

**Acceptance Scenarios**:

1. **Given** 通用内容存储模型，**When** 接入一个新模块的内容，**Then** 无需新增针对该模块的专用表结构即可存放其列表型内容与「页面形状」型内容。
2. **Given** 通用导入机制，**When** 为新模块提供数据文件，**Then** 同一导入命令能按模块导入并通过条数校验。

---

### Edge Cases

- **内容为空 / 未导入**：API 返回空集合而非错误；前端渲染空状态。
- **存储不可用**：内容 API 返回明确错误状态，前端展示可读错误，不泄露内部细节。
- **重复导入 / 并发导入**：幂等保证不产生重复；以唯一键 + 内容指纹判定是否更新。
- **数据文件损坏 / 字段缺失**：导入校验失败并报错，拒绝写入残缺数据。
- **既有会话/对话数据不受影响**：新增内容相关存储不得改动现有 sessions/conversations/messages 结构与行为。
- **生产环境启动**：默认不在启动时自动导入，避免拖慢/污染生产启动；导入走显式命令。

## Requirements *(mandatory)*

### Functional Requirements

**内容存储模型**

- **FR-001**: 系统 MUST 提供一种**模块无关**的内容存储模型，以 `module`（jargon/job/code/lab/chat）维度区分内容，支持三类形态：(a) 列表型条目（术语/题目/工具/命令/步骤），(b) 分类/树（侧边栏），(c) 非列表的「页面形状」元数据（如标签集合、Tab 描述、阶段排序）。
- **FR-002**: 列表型条目 MUST 将用于**过滤与排序**的字段（如所属模块、条目类型、分类、难度、来源、排序位）作为可检索的结构化字段，其余完整内容以整体文档（JSON）形态存放，便于不同模块承载差异化、含嵌套数组的内容。
- **FR-003**: 每个条目 MUST 具备在其模块内稳定且唯一的标识（用于幂等导入与详情读取）。
- **FR-004**: 内容存储的引入 MUST NOT 改动既有 sessions/conversations/messages 的结构与行为；内容相关表以「不存在则创建」方式与既有初始化流程一致地建立。
- **FR-005**: 存储模型 SHOULD 兼容未来迁移到更重的数据库（如将整体文档字段平滑升级为原生 JSON 类型），避免重构式 schema 变更。

**内容导入（Seed）**

- **FR-006**: 系统 MUST 以**可审查的数据文件**（按模块组织）作为今后内容的唯一来源，旧 DC 框架文件退化为历史参考。
- **FR-007**: 系统 MUST 提供**幂等**的导入机制：重复导入在数据未变时为无操作；数据变更时仅更新受影响条目（基于唯一键 + 内容指纹判定）。
- **FR-008**: 导入 MUST 支持**显式命令触发**（可按模块、可强制全量），作为主路径（供 CI / 部署使用）。
- **FR-009**: 导入 MAY 支持在应用启动时自动执行，但 MUST 默认仅在开发环境开启、生产环境关闭（通过环境开关控制）。
- **FR-010**: 导入 MUST 包含**条数校验断言**（如 Jargon 词条数与数据文件一致）；校验不通过时显式失败并报告差异，拒绝静默写入残缺数据。

**内容读取 API**

- **FR-011**: 系统 MUST 提供**只读、公开**的内容读取接口（无需会话/鉴权），至少实现「按分类分组返回 Jargon 术语树」。
- **FR-012**: 列表型读取接口 SHOULD 仅返回轻量字段（用于列表展示），完整内容经详情接口按标识获取；本 Spec 的 Jargon 因数据量小，可一次性返回完整分组树。
- **FR-013**: 内容读取接口 SHOULD 返回适当的缓存提示（内容近乎静态），以便前端/浏览器缓存。
- **FR-014**: 内容读取接口的实现 MUST 沿用既有后端的 router/service/数据库访问分层模式，并注册进既有应用入口。

**前后端契约与渲染**

- **FR-015**: 系统 MUST 在共享类型包中定义内容相关的类型（至少 Jargon 术语与其响应信封），作为前后端跨层契约。
- **FR-016**: 名词页 MUST 改为从内容读取 API 获取数据并渲染；交互逻辑（分类展开/折叠、术语选中、占位/加载/错误状态）保留在前端，**内容数据不再硬编码于前端**；页面词条计数 MUST 由数据动态计算。
- **FR-017**: 前端 MUST 遵循固定设计系统（品牌绿 `#00ffa0`、字体 JetBrains Mono / Inter），改造后名词页视觉与改造前保持一致。
- **FR-018**: 前端在内容获取失败或为空时 MUST 呈现友好状态，不白屏、不抛未捕获异常。

**关注点分离（宪法约束）**

- **FR-019**: 前端 MUST NOT 直接访问数据库；所有内容经后端 API 获取。
- **FR-020**: 后端 MUST NOT 承载 UI 呈现/动画逻辑；仅提供内容数据。任何交互、动画、计算逻辑不得序列化进存储。

### Key Entities *(include if feature involves data)*

- **内容条目（Content Item）**：一条可独立展示的教学内容（此 Spec 中为一个术语）。关键属性：所属模块、条目类型、所属分类、模块内唯一标识、列表展示标题、用于过滤排序的结构化字段、完整内容文档、内容指纹、时间戳。
- **内容分类（Content Category）**：模块内的一个分组（此 Spec 中为术语的 6 个分类之一）。关键属性：所属模块、标识、显示名、排序位、适用的条目类型。
- **内容元数据（Content Meta）**：模块级、非列表型的「页面形状」数据（本 Spec 暂不强制使用，为后续模块预留，如标签集合、Tab 描述、阶段排序）。关键属性：所属模块、键、内容文档。
- **内容数据文件（Content Fixture）**：按模块组织、可审查、可版本管理的内容来源文件，导入机制据此写入存储。
- **术语（Jargon Term，条目的一种具体形态）**：emoji、中文名、英文名、通俗解释、技术解释。（旧版另有「关联术语」「是否新增」字段，当前迁移源不含，列为未来增强。）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 学生访问名词页时，看到的术语与分类数量与入库 fixtures 一致（当前 36 词条 / 6 分类，计数动态显示），且全部内容来自后端提供而非前端内联。
- **SC-002**: 内容维护者修改一条内容并运行导入后，刷新页面在 1 分钟内即可看到更新，全程未改动任何前端组件代码。
- **SC-003**: 在数据未变的情况下连续运行导入两次，第二次为无操作——记录总数不变、无重复、无报错。
- **SC-004**: 当数据文件条数与校验值不符时，导入 100% 显式失败并报告差异，不写入残缺数据。
- **SC-005**: 名词页所有交互（分类展开/折叠、术语选中、占位/加载/空/错误状态）均正常，浏览器控制台零未捕获错误。
- **SC-006**: 后续任一模块（Job/Code/Lab/Chat）可在**不修改**本 Spec 所建存储模型/导入器核心的前提下，仅通过新增数据文件与模块端点接入。
- **SC-007**: 既有聊天/会话功能（发送消息、查看历史对话）在本 Spec 落地后行为不变，无回归。

## Assumptions

- **数据存储采用 SQLite 作为 v1**（用户决策），后续版本再迁移到更重的数据库（Postgres，部署编排已就绪）；本 Spec 在存储设计上为该迁移预留平滑路径，但**不在本 Spec 内实施** Postgres 迁移（YAGNI）。
- **Spec 005 以 supersede 方式取代**（而非原地修订），并在本 Spec 顶部声明取代关系。
- **`packages/content` 旧方案归档 / 暂存**：不做删除式改动、不采用；允许在其 `README` 标注「已归档，不再使用」，目录与代码保持原样（见 Clarifications）。
- **SQLite `.db` 文件不纳入版本控制**：以文本型 JSON fixtures 作为 git 内容来源，`.db` 为生成产物，落地时加入 `.gitignore` 并移出跟踪（见 Clarifications）。
- **内容条目暂不引入 version/status/locale 等内容管理字段**（YAGNI）；若未来上内容管理后台，应尽早补列——本 Spec 记录该风险但不实现。
- **Jargon 作为样板切片折入本 009**（而非独立 Spec），以保证 009 具备用户可见产出；其数据来源为现有前端内联的 43 词条 `CATEGORIES`，内容不重写、仅搬运与改连。
- 内容为只读公开资源，本 Spec **不含**内容写入/管理 API（导入是唯一写入方）；teacher-admin 写接口为未来 Spec。
- 服务端渲染拉取时直连后端服务（而非经浏览器代理）的可达性，由实现阶段在开发与容器环境分别确认。
- 现有后端初始化、分层（router/service/db）与既有内容数据（前端内联术语）真实可用，作为本 Spec 的依赖与素材。
